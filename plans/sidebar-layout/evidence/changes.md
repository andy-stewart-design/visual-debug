# Approved changes

- **Step 2.3 conservative error badge:** the user said the `!` badge on reload/restricted pages was unnecessarily alarmist and explicitly requested explanations for restricted pages, with `!` only for genuine errors. Step 2.3 now includes the shared feedback classifier, navigation reset/invalidation, and its regression tests; R3/AC15 and final acceptance mappings record that policy. This does not suppress genuine unexpected failures, change page permissions, or authorize Phase 3/native acceptance.

- **Step 2.3 persistent website access and direct sidebar Start:** after the sidebar could not start on a newly opened tab without the toolbar, the assistant explained that the current active-tab toolbar grant could be broadened through a one-time browser approval so ordinary HTTP/HTTPS sites retain access. The user explicitly agreed: **"ok, let's give that a shot then"**. This supersedes the earlier no-persistent-host-permission policy for the bounded `http://*/*` and `https://*/*` origins only. The approved contract adds browser-granted persistent site access, direct sidebar Start after the grant, and unavailable guidance when it is absent; it does not add `<all_urls>`, `file:`, `ftp:`, internal-page access, automatic scripting, `permissions.request`, or a promise that every unpacked reload shows a prompt. Browser controls/site settings own installation, update, and grant changes. Step 2.3 records the implementation and pending native/manual proof; the Phase 2 gate remains after it.

- **Step 2.1 reload/reactivation repair:** the user's screenshot and reload → toolbar bug report requested correction of page/sidebar desynchronization and the error badge. The reconciliation repair remains within existing navigation/state requirements; the related badge regression additionally touches `lib/activation.ts` and its existing unit tests. Step 2.1's expected-file/verification references include that coupled repair. No new product behavior, permissions, acceptance waiver, or phase advancement is authorized by this bug report.

- **Step 2.1 Alt+wheel safeguard:** after reporting Firefox Alt+scroll history navigation, the user answered "yes plz" to a proposed non-passive page listener scoped to active inspection, consuming Alt+wheel while preserving ordinary scrolling and removing the listener on Stop/Exit. The approved addition is implemented in the session-owned modifier controller with DOM cancellation/cleanup tests. Spec R11/AC13, Step 2.1's file scope/task/checks, and future final/regression acceptance mappings now include this behavior; existing IDs are preserved. This is not permission to change browser preferences or block gestures while inspection is stopped, nor is it a native Firefox runtime pass.

- **Firefox test target and manual ownership:** the user said "dev edition is fine" and "i do all manual checks". The bounded Firefox runtime target is therefore Firefox Developer Edition, not stable Firefox, and all manual browser verification belongs to the user. Spec/overview/plan wording now reflects this; Developer Edition results must not be represented as stable-Firefox coverage.
- **Step 0.1 prerequisite repair:** after the reported Firefox startup error was confirmed as a Manifest V2 `browserAction` versus Manifest V3 `action` mismatch, the assistant asked to add a small prerequisite fix and regression test before continuing. The user answered "yes". Step 0.1 now includes the shared API resolver, both existing consumers, focused tests, and repeat deterministic checks. No sidebar implementation, manifest-version change, permission expansion, or waiver of runtime verification was approved.
- **Step 1.1 validator cleanup:** after review identified avoidable protocol casts and unchecked optional legacy fields, the user requested "let's clean this up before moving onto 1.2". Cleanup is confined to protocol validation and its tests: preserve public/wire types and original objects, remove assertions, and reject malformed optional legacy fields. This does not authorize Step 1.2 or alter its gates.
- **Step 1.2 architecture/conventions refactor:** after reporting "This is working," the user identified PascalCase filenames, missing CSS Modules, and a monolithic sidebar component, requesting smaller components for safe later removal/refactoring. The approved refactor renames the entrypoint to `sidepanel-app.tsx`, extracts `use-sidebar-connection.ts`, and adds convention-matching sidebar shell/status/instructions/controls folders with `index.tsx` and `styles.module.css`. Step 1.2's expected files/refactor task and Step 2.1's renamed/modular file references are updated; IDs, dependencies, behavior, and acceptance gates are unchanged. This request does not invent itemized exceptional-case or delayed-start runtime proof.
